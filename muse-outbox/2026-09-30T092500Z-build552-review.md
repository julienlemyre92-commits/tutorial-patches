## Verdict: one concrete defect — the burn path ignores the Make-X interface

**Location:** `makeBurntMeat`, lines 450–457:


**Proof it waits on** (line 331): `case BURN_MEAT: return f.count(BURNT_MEAT) >
p.before.count(BURNT_MEAT);` — only satisfied when item 2146 appears in
inventory.

**Why it blocks:** using cooked meat (2142) on the Rimmington range opens the
standard Make-X cooking quantity interface ("How many would you like to
cook?"). Wiki evidence, retrieved today:
- Burnt meat page, Creation tabber: `{{Recipe |skill1 = Cooking |...|ticksnote
  = Make-X is 1, 3, then 4 ticks |mat1 = Cooked meat |output1 = Burnt meat}}`
  — the deliberate burn is a Cooking *skill action* through Make-X, not a
  direct item-on-object transform.
- Burnt meat page text: "deliberately make burnt meat **by cooking** a piece
  of cooked meat"; per-burn chatbox "You deliberately burn the nicely cooked
  meat."

The branch issues the use-action and then waits 10 s for a 2146 that cannot
arrive — nothing ever clicks a quantity. After 3 timeouts `verifyPending`
calls `hold("Unproved burn:cooked-meat after 3 attempts; ...")`: a **hard HOLD
mid-quest** at MAKE_BURNT_MEAT.

**The correct pattern is ten lines below in the same method** (lines 460–471):
the raw-beef path checks `f.production` (the Make-X widgets 270/14 and 300/16,
detected in `observe()` lines ~247–250), then clicks the product via
`findCookProduct` — which already matches `COOKED_MEAT` (line ~481:
`widget.getItemId() == COOKED_MEAT || widget.getItemId() == RAW_BEEF`). The
burn branch needs the same two-step: use 2142 on 9682 → on `f.production`,
click quantity 1 → then expect the 2146 proof.

- `Rs2Shop.buyItem(int, String)` exists — the shop path's `buyItem(item, "1")`

**Confirmed vs uncertain:**
